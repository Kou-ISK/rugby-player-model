# 本人とCodexの最初の研究実験

[English](RESEARCH_LOOP.md) | [日本語](RESEARCH_LOOP.ja.md)

このloopの目的は、本人の指導を条件付き仮説として明示し、適用場面と反例の両方で試して残すことです。動作が変わるだけでは改善とは判定しません。実施状況・本人の評価・採否は各sessionの記録で確認します。

## 会話で研究を進める役割と区切り

研究対象は、限られた知覚と記憶から関係・行為可能性を推定し、目標に照らして行為を選び、実行後の観測で維持・修正する仕組みです。生成場面はその仕組みを識別する刺激として使います。指導者の説明だけで人間の認知過程そのものを測定したことにはなりません。

本人は場面の意味を確認し、選手への指導・判断が変わる手掛かり・例外を伝えます。Codexは研究の進行、場面準備、表示、原文と解釈の分離、仮説・対照・結果の記録を担当します。本人に次のコマンドや試験方式を選ばせて会話を止めません。

1. **現在地を伝える。** 調べる問い、現在の段階、今回本人にしてほしい一つのことを示す。画面が動作試行、仮説形成用の配置比較、モデル評価のどれかを明示する。
2. **意味を確かめて指導を受ける。** 誰が味方か、対象や身体方向などの不備があれば先に修正する。見せた入力を保存し、通常は一度に一つの具体的な質問をする。操作の失敗を認知判断として採点しない。
3. **新しい情報を整理する。** 「使った情報→予測する関係→選択・継続・中止の条件」のうち今回増えた点だけを短く記す。本人の明示事項、助手の解釈、未確認事項を分け、原則全文の作り直しを繰り返さない。次の判断を変える曖昧さだけを聞く。
4. **大枠の確認・比較・統合・道具の修正から次を選ぶ。** 下記の質問条件に従います。 距離・向き・運動・観測の新鮮さなどから、競合する説明を見分ける変更を一つ選ぶか、一群の指導をまとめる工程へ移る。比較する場合は、何を固定し、何を変え、何を確認するかを先に記録し、場面と質問を提示する。本人の答えや場面妥当性の確認を先回りして生成しない。
5. **原則の整理と実装を分ける。** 探索中は考えられる認知機構と不足する根拠を記録し、直ちにコードへ反映しない。後の実装段階で選手モデルの実行案と判断原則の文章案へ分け、未対応の機構はコード案として扱う。動作確認のための重み変更・強制行動・描画成功を、認知機構の改善に読み替えない。判断原則は同じ観測への原則なし／旧版／新版を独立に評価する。
6. **区切りと次の一手を残す。** この往復で分かったこと、残る不確かさ、次の行動と理由を短く伝える。新しい場面・質問は毎回必須ではない。候補採用時だけ対象と版を示して選手モデル／判断原則別に本人の判断を待つ。次の場面は仮説を識別するために選び、場面数や成功数だけで終了しない。

各sessionの `work/research-checkpoint.md` に、現在の問い・段階・source snapshot/候補/表示応答・本人の発言と未確認の解釈・次の比較・予測と反証条件・次の質問・実行能力の不足をまとめたcheckpointを保存します。これは私的研究ノートであり、state.jsonの実験記録や本人の承認の代用にはしません。再開時は表示と記録を確認してから現在地を説明します。

道具の不具合で今回の知覚・結果の意味が変わる場合は、その判断の採点を止めて修正します。必要能力がない場合も、その結果についての検証だけを保留し、独立して進められる指導の解釈や配置の確認を示します。実試合映像には進みません。

事前凍結・匿名判断原則比較・首振り履歴の現行手順は [EVALUATION_PROTOCOL.md](../../../evaluation/PROTOCOL.ja.md)。未使用条件で試す場合、指導を入力する前にfreezeします。固定8ケースだけでは未知への転用評価を完了した扱いにしません。

## 大枠を整理してから、説明を識別するケースへ進む

開始・再開時は、[公開テンプレート](RESEARCH_CHECKPOINT.ja.md)を使う私的な `work/research-checkpoint.md` を入口にします。まず対象となる役割・局面について、目的、維持する関係、崩れ方、修復を整理します。索引にある指導を再利用し、不足だけを確認します。場面を見せていなくても、大枠の確認は適切な次の行動です。この整理は仮説であり、脳の装置や必須の直列処理構造を確定するものではありません。

詳細な比較の前に、テンプレートの質問カードへ、親の問い、未解決の区別、競合する説明と異なる予測、固定／変更条件、必要能力、観測内容、枝を区切る条件を記します。両説明が同じ答えを予測するなら比較を作り直すか、大枠へ戻ります。関連する関係を変えずに数値だけを変えても、有用な対比にはなりません。

回答済みの区別、不適切とされた前提、親の問いを変えない細部は保留します。結論、不確かさ、理由、再開条件を残し、別の有用な不足を選びます。毎回答後に新しい場面を強制しません。研究方法への質問は手順・checkpointへ反映し、選手への指導にはしません。

## 段階の移行条件と品質

| 段階 | 作業と根拠 | 次へ進む条件 |
|---|---|---|
| 大枠の整理と探索 | 目的、関係、崩れ方・修復、役割・情報条件の範囲、指導原文、不確かさ | 対象範囲の不足と代替説明を特定できる。全ラグビー状況の網羅は要求しない |
| 識別できる比較と統合 | 事前予測、適切な動的刺激、取得入力、反例、矛盾する報告 | 根拠が説明を区別できる。できなければ課題を直すか、機構を未解決として残す |
| 機構の設計 | 情報・履歴・不確実性・行動の明示的な操作、簡単な競合モデル、同じ身体能力 | レビュー可能な提案と反証可能な評価計画。パラメータを当てはめる場合は、推定値を解釈する前に合成データでパラメータ／モデルを識別できるか確認する |
| 相互作用 | 独立した観測・記憶で反応し合う選手、制御した変化と修復 | 隊形の座標を与えず連携を生成する。共有制約×局所調整を比較し、集団の指標は評価者だけが使う |
| 人による支持と転移 | 人の時間的な行動、情報への介入、未見条件、独立した再現 | 指導された行動名以上の根拠でモデルを区別する。支持された処理と範囲を報告し、神経実装の同一性の証明とはしない |

実行モデルと単独で使う判断文書の提案・評価・採否は独立です。文書は同じ匿名入力への原則なし／旧版／候補で評価します。段階の移行や試験成功は、採用の許可ではありません。

協調では、他選手のコース・速度・役割が変わると誰が調整するか、担当の重複・空白が生まれるか、パスや守備に有用な関係をどう回復するかを調べます。台本のある選手は探索時の手掛かりを比較できますが、相互適応の証拠ではありません。共有戦術は知っている制約であり、全員の現在位置を知る権限ではありません。[認知研究](../../../docs/COGNITIVE_RESEARCH.ja.md)と[実装の限界](../../../docs/LIMITATIONS.ja.md)に従います。

推奨、本人の体験報告、計測した行動を分けます。取得可能だった情報だけで注意や想起を認定しません。カメラ方向は視線ではなく、停止中の見回しでは時間が進まないため人の反応時間を検証できません。必要な計測や動作が未対応なら不足を記録してその主張を保留し、仮想の結果を証拠にしません。

この条件は協力者への指示とレビュー用の記録であり、実行時に研究方法の遵守を強制する機能ではありません。新しい会話ではcheckpointと原記録を読みます。ソフトウェア試験だけではAIが方法を守ることを証明できません。

## 原則の探索を先に進め、モデル実装と分ける

最初は幅広い指導を集め、暫定的な原則を洗い出します。関連する根拠の整理は継続的な分析であり、そのたびにモデルを更新する工程ではありません。ここでの学習は研究上の知識の蓄積と仮説の更新を指し、指導を保存しただけでAIの重みや実行モデルが学習する意味ではありません。ツールへAI APIを組み込みません。

一つの保持者・パスのパターンに留めず、保持者と非保持サポート、守備とカバー、局面の変化、情報の有無・古さ・声、共有する戦術上の制約と局所的な連携へ調査範囲を広げます。場面数の達成ではなく、新しい手掛かりや競合する説明を識別するために次を選びます。調査範囲の表を残し、似た例が多いことを幅広く調べたことに置き換えません。

知覚・注意・記憶した情報・関係の予測・目標・行動・再観測を、研究内容を整理する暫定的な枠組みにします。何が得られ、何に注意し、何を記憶から使ったかは根拠のある範囲で記録し、行動名だけから本人の内的過程を推測しません。観測時刻・確信度・不足情報・許容できる複数の選択肢・切替条件を保持します。人間の認知・記憶との同等性は理論と行動の別途検証を要する研究課題であり、指導への適合だけで達成した扱いにしません。

- **各回答の直後：** 指導原文と証拠の種類を即時保存します。場面に対応する指導は取得済みsnapshot・区間を保存し、`propose` で空の選手モデルpatchと未完成の原則欄を持つ未採用候補にします。口頭のみの指導は、説明された前提と原文を私的ノートへ保存し、観測参照を空にします。無関係なsnapshotで代用しません。新しい手掛かり、矛盾、次の行動だけを短く記します。研究方法の相談は選手への指導ではありません。一群が終わるまで保存を遅らせません。
- **指導を集める間：** 選手モデル・判断原則・エンジンの基準版を固定します。似た場面を増やすのではなく、競合する説明や例外を見分ける条件を選び、変更する刺激を提示前に記録します。証拠の意味を変える道具の不具合は先に直し、影響した記録を残して変更前後の条件を分けます。
- **探索中の区切り：** 必要に応じて増えた原則・矛盾・不足を短くまとめ、有用な比較や未調査の役割へ進みます。一定数の場面を終えたら実装する、という基準は設けません。現行モデルとの不一致は限界として記録し、直ちに収集を止めたりモデルを調整したりする理由にしません。有効な観測・記録を妨げる道具の不具合は先に直します。
- **統合時：** 索引から根拠をまとめて読み、暫定的な主張に元候補ID・revision・snapshotを結び付けます。一つのパターンに一つの行動を割り当てず、代替行動や例外も残します。原記録を保持し、回答ごとの詳細な定式化や自動採用は行いません。
- **後の設計・実装段階：** 関連する役割・条件を調べたか、競合する説明や反例を検討したか、認知・記憶の操作を入力・出力・不確実性・反証可能な予測として定義できるかを見直します。不足していれば必要な根拠を集めます。この研究段階に進む条件が整ったところで、実行モデルと判断文書の変更案、比較計画を別々に作ります。既存runnerの項目を認知構造の設計範囲の上限にせず、未対応機構は架空のpatchではなくレビュー可能なコード案にします。
- **検証時：** 予測・失敗条件・変更案の版を固定して変更前後と関連する回帰条件を比較します。指導済み条件への適合は、未知条件への転用の証明ではありません。未使用条件は[評価手順](../../../evaluation/PROTOCOL.ja.md)に従い、その指導・露出より先に確保・凍結します。実装を変えたときに必要な技術検証を行い、実際の変更・結果・限界を示した後で成果物別の採否を本人に確認します。

私的な一群の索引には、問い・固定版・根拠への参照・短い所見・未解決点・統合状況・次の行動を残します。contextやtrace全文は私的ファイルへ保存し、推論には必要部分を抽出して、同じ全文を繰り返し出力しません。回答ごとの全文改稿、モデル未変更の比較実験、成功済み検証の反復を避けます。刺激が変わった場合や表示が曖昧な場合には確認しますが、研究進行のための定例的なcomputer useは必要にしません。これにより重複するトークン使用を減らすことを目指します。場面数だけで削減量を推測したり、利用量の根拠なしで削減実績を主張したりしません。

## 1. 場面と指導を保存

汎用CLI例は、[研究開始手順](RESEARCH_START.ja.md)で設定した `RPM_SESSION_DIR` と既存の `work/` を前提とします。設定済みMacでは[専用launcherと私的保存先](MAC_START.ja.md)を使います。

一人称で首を振る／再生／停止し、短い指導を入力して候補を保存します。scene・seed・time・player、身体／首、観測と履歴、profile、選手モデル／判断原則基準版を記録します。`context CANDIDATE_ID` または「Codex用の観測contextを保存」でCodexへ渡します。世界真値のenvelopeは含まれません。

本人への聞き返しが必要なのは、指導がどの観測条件に適用され、何を変えずに残すかが不明なときです。Codexは候補を編集できますが、本当の研究原則の採用を代行しません。

## 2. 条件・例外・予測・反例を書く

この工程は各回答の直後ではなく、指導をまとめる区切りに行います。[合成例](../examples/conditional-coaching-edit.json)は「保持中で新鮮な受け手情報がなければ再観測する。ただし観測上の近い脅威は例外」です。`notes.rationale` に指導から変更案への理由、`expectedEffect` に対象場面の予測、`counterexample` に変えてはいけない条件を書きます。判断原則の条件・判断基準・優先度・例外・不明時・根拠は独立に編集します。

```sh
npm run --silent bridge -- context CANDIDATE_ID > "$RPM_SESSION_DIR/work/context.json"
npm run bridge -- edit CANDIDATE_ID --file "$RPM_SESSION_DIR/work/edit.json" --revision CONFIRMED_REVISION
```

選手モデルの限定的な宣言ルールは次の語彙を使います。scene・seed・見えない選手・将来の真値で分岐する欄はありません。新しい機構が必要なら、候補JSONで表現したふりをせずコード差分として研究します。

| 欄 | 選択肢／意味 |
|---|---|
| `when.possession` | `any` / `has-ball` / `no-ball`。自己の合成保持感覚 |
| `when.evidence` | `no-fresh-receiver` / `fresh-receiver` / `stale-player` / `heard-call` / `missing-player-vision` / `observed-ball`。現在の観測と記憶に由来 |
| `when.unlessCloseThreat` | 観測上の近い脅威があるなら適用しない。隠れた脅威が不存在という意味ではない |
| `action` / `weight` | scan・hold・carry・pass・supportのスコアへ−2〜2を加算。戦術との混合前で、硬い実行資格は変更しない |
| `call`（任意） | `support-call` / `warning-call`。その規則の行動が選ばれた場合だけ意味的イベントを出す |

`contextRules` は最大32個・一意IDの配列です。編集は配列全体を置換するので、残す既存原則も含めてください。複数の該当規則は加算されるため、重複した意味の規則が過大な重みを作らないかレビューします。個人選好や戦術遵守が強ければ予想と違う行動になることも試験対象です。callは音声合成でも他選手の反応でもなく、自己の新しい聴覚証拠へ戻しません。

## 3. 未採用のまま実験を記録

「未採用候補で再実行・記録」で1〜20stepを実行します。1stepは0.2秒。記録場面と8つの固定回帰ケースを、指導候補のprofileを全てへ固定してbefore/afterで再生します。事前凍結setを候補作成時に選んだ場合は、別のfrozenTrialsも保存します。行動が違えば、その後の観測が異なることはあります。

```sh
npm run --silent bridge -- run CANDIDATE_ID --revision CONFIRMED_REVISION --steps 5 --mode preview > "$RPM_SESSION_DIR/work/experiment-preview.json"
npm run bridge -- experiments
npm run --silent bridge -- experiment EXPERIMENT_ID > "$RPM_SESSION_DIR/work/experiment.json"
```

`preview` 簡易比較は保存ファイル自体を変えません。`run --mode preview` は実験記録だけを保存し、有効な選手モデル／判断原則や採用状態を変えません。各実験は候補全文・revision・理由・初期入力・before/after 選手モデル・判断原則文書／構造化追加原則・各step trace・coreソース識別を固定します。Node/platform/arch、Git commitとdirty状態、lock・snapshot・結果・判断原則文書のSHA256も保存します。snapshotと結果のhashは保存オブジェクトの `JSON.stringify` UTF-8に対するSHA256です。Git情報を取得できないコピー配布ではnullと記録し、成功を推測しません。保存結果の表示は再計算しません。ソースを書き換えた場合はserverを再起動してから記録します。

合成例の期待差分は記録場面carry→scan、別場面carrier-openもcarry→scan。一方、圧力下hold、新鮮な受け手pass、非保持supportは維持します。5種類すべての定数行動stubと旧 `scanBias:2` はこの受入条件に失敗します。これは仕組みを確認する回帰試験であり、公開された8ケースを将来も「未知」と呼べません。実研究では本人が未使用の場面・条件を別途選び、候補作成前に予測と失敗条件を記録します。

## 4. 本人が差戻し／採用する

差戻しには理由が必要です。いずれかの選手モデル／判断原則がレビュー済みになると元候補は不変です。「同場面で新候補」は観測・記憶・profileを保持し、現在の承認選手モデル／判断原則を基準として親ID付きの新しいpending候補を作ります。コピーされた差分は新しい基準に対して再点検します。特にcontextRulesの全置換による既存原則の消去に注意します。

```sh
# このreturnは本人が意図して実行する操作
npm run bridge -- return CANDIDATE_ID --target player --by owner --revision CONFIRMED_REVISION --reason "差戻し理由"
# 派生候補を作るだけでは採用されない
npm run bridge -- revise CANDIDATE_ID --revision CONFIRMED_REVISION --reason "修正方針"
```

内容を確認した本人が選手モデルと判断原則を別々に採用します。選手モデルだけ採用して判断原則を保留することも可能です。同じ判断原則IDを改訂すると現行文書では置換し、旧版には旧文章を残します。別クライアントが候補を編集するとrevision競合409で拒否し、再確認が必要です。最新revisionを自動取得して承認する処理を作りません。

採用後は `run --mode active` または「現在の承認版で再実行・記録」を実行し、採用前の記録と比べます。合成試験のowner操作は実研究原則への本人承認ではありません。

## 5. 判断原則を独立に試す

保存した実験を選び「匿名判断原則入力」。または以下を実行します。

```sh
npm run --silent bridge -- judgment-packet EXPERIMENT_ID --arm after --cases frozen > "$RPM_SESSION_DIR/work/judgment-after.json"
npm run --silent bridge -- judgment-evaluator-map EXPERIMENT_ID > "$RPM_SESSION_DIR/work/judgment-evaluator-only.json"
npm run --silent bridge -- export-judgment-json > "$RPM_SESSION_DIR/work/judgment-current.json"
npm run bridge -- judgment-review EXPERIMENT_ID --file "$RPM_SESSION_DIR/work/judgment-response.json"
```

model用入力は指定した一群の判断原則文書／構造化追加原則と匿名ケースだけです。原則なし群は --arm none、before群は --arm before。固定回帰には --cases regression を指定し、未見と呼びません。評価用ラベル・scene・seed・採点基準・選手モデル結果・worldは別の評価側対応表に残し、モデルへ渡しません。構造化JSONは追加原則であり、baseline全文の機械構造化を主張しません。

本人が原則なし／before 判断原則／after 判断原則それぞれの新しい会話を作り、その群に割り当てた判断原則文書（原則なし群には無し）と共通の観測ケースだけを渡します。それぞれの新しい会話へ対応する一群の匿名入力だけを渡し、他群の回答・評価側対応表・選手モデル結果は持ち込みません。[判断原則評価手順](../../../models/judgment/docs/REVIEW.ja.md)に沿い、判断・使った原則・不確実性・反例・自己レビューを求めます。UIまたは以下のJSONで回答を保存します。

```json
{"arm":"after","group":"frozen","model":"実際のモデル名・設定・実行日","output":"回答全文（条件名を含む）","assessment":"本人の採点、未確認事項、反例"}
```

保存は実験への紐付けであり、正しさを承認する機能ではありません。記録は常に `unverified-external-response` / `humanValidated:false`。原則準拠とラグビー上の妥当性を分けて本人が判断します。API・課金・外部自動送信は追加していません。今回の合成mockは判断原則の実際の生成AI評価ではありません。

## 6. 復元して次の仮説へ

本人が選手モデル／判断原則ごとにundoします。承認・差戻し・親候補・保存実験・判断原則回答は消えません。Control-Cで停止して再起動し、「候補の場面を復元」で記録時の身体／首／履歴／profileへ戻します。実行ルールは現在activeの承認版です。古い実験結果はそのまま読み、旧エンジンの再実行にはそのGit版を使います。

状態は明示した私的sessionへ保存します。長い履歴を蓄積する本格運用の前にはバックアップとストレージ拡張を検討します。初回の本人受入では「画面で見えた情報」「指導の意図」「適用条件と反例」「独立選手モデル／判断原則の判断」「復元できたか」を私的記録へ残します。[Mac受入記録](../../../docs/verification/MAC_ACCEPTANCE.md)は過去の手順・証拠の参照であり、上書き先ではありません。

## 過去の0.3.0導入時の互換性と移行

これは当時の変更記録です。現行保存形式はLOCAL_STORAGE、API 11の継続保存はLOCAL_BRIDGEを参照してください。研究上のundoとコードdowngradeは別です。

| 対象 | 互換性／操作 |
|---|---|
| package | 0.1.0／0.2.0→0.3.0。依存version／解決先は不変、lockのpackage版だけ更新 |
| 観測／snapshot | contractVersion 1を維持。旧3fixtureをそのまま読み、通常の数値ルールは同じ判定を返す |
| 選手モデル trace | 新規実行はcognition-0.3／appliedRules付き。JSON Schemaは旧cognition-0.2 traceも読む |
| 私的session | format 1の旧候補・版・履歴を保持。experiments／bReviews／evaluationSetsが無ければ空として読む。原則を自動採用しない |
| bridge | API 2／3→4。旧serverを止めて新しいコードで再起動。旧serverへの新UIの書き込みは拒否 |
| 判断原則 | 凍結初期判断原則＋明示採用した追加原則。既存判断原則評価baselineとroot 判断原則ドラフト0.1は今回変更しない |

コードを戻す際はsessionも更新前バックアップへ戻す別作業です。新形式で書いたsessionを旧コードへ上書きで読み込ませる前方互換性は保証しません。選手モデル／判断原則の研究上のundoはコードのdowngradeとは別操作です。

## 保存した現在位置から先へ試行する

`run CANDIDATE_ID --revision N --steps 7 --mode preview --start snapshot` は、候補に結び付いたsnapshotの位置・時刻・取得済み記憶から先へ進む。既定の `--start coaching` は従来どおり指導区間の開始へ戻り、区間末尾で停止する。未来の試行と過去の再検証を混同しない。

保存結果の `recordedInput.source` は `captured-snapshot`、`window` はnullになり、元の指導区間はcandidate内に保持される。比較表示は既存の `view-request compare` で行う。previewは選手モデル／判断原則の採用を変更しない。一時的な実行補助の重みを使った試行は、その旨をnotesへ記し、一般原則の獲得や本人の研究承認とは扱わない。
